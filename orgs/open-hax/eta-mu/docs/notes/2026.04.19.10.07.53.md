# I need you to grok the  current contract system status in knoxx before you write any specs so you know where we are starting frm

Short version: in Knoxx today, “contracts” are **editable EDN blobs stored in Redis with a thin admin API and a compile-to-SQL shape, but there is no real runtime, no type system beyond two fields, and nothing wired into openplanner/actors yet**.

## What’s actually implemented

### Storage \& indexing

- Contracts are stored as raw EDN strings in Redis under keys like `contract:edn:<contract-id>`.
- A Redis set `contracts:index` holds the list of contract IDs; listing contracts just reads that set and fabricates stub metadata (kind `"agent"`, version `1`, enabled `true`, hash `0`, `compiledAt` `nil`, `updatedAt` = now) rather than reflecting the real EDN content.

So: **Redis is the only source of contract definitions right now, and the “list” view is basically a fake index.**

### EDN shape \& validation

`validate-contract-edn` currently does only three things:

- Trims the text, errors if empty.
- `reader/read-string` to get a Clojure map.
- Checks:
    - `:contract/id` exists and is a string.
    - `:contract/kind` exists and is a keyword.

Everything else in the EDN is opaque; there is **no validation of your taxonomy** (trigger/policy/tool-call/etc.), no schema for `:events`, `:contract/uses`, or `:data/tools` beyond being present/absent.

So: **the contract “model” is just “any EDN map with two well-typed fields.”**

### Compile step: extracting a SQL-like projection

`compile-contract->sql` is the most structured part:

Given a parsed contract map, it produces:

- `:contract` row:
    - `:id` = `:contract/id`
    - `:version` = `:contract/version` (default `1`)
    - `:kind` = `(name (:contract/kind ...))` (string)
    - `:enabled` = boolean of `:enabled` (default `true`)
    - `:edn_text` = full `pr-str` of the contract
    - `:edn_hash` = Clojure `hash` of that string
    - `:compiled_at` = ISO timestamp.
- `:event-kinds` rows:
    - Looks under top-level `:events`, then:
        - `:always` → rows with `:mode "always"`.
        - `:maybe` → rows with `:mode "maybe"`.
    - Each row: `{ :contract_id id, :event_kind (name k), :mode ... }`.
- `:bindings` rows:
    - Read from `:contract/uses` (default `[]`).
    - Each dep becomes `{ :contract_id id, :dep_id (name dep) or (str dep), :load_order i }`.
- `:tools` rows:
    - Read from `[:data :tools]` or `[:data/tools]` (default `[]`).
    - Each tool `t` becomes `{ :contract_id id, :tool_name ... }` using a best-effort:
        - keyword → `(name t)`
        - string → itself
        - map → `:toolId` or `:tool/id` or `str t`.

**Critically:**

- This function *only builds a data structure*; the “compile” HTTP endpoint returns that structure in JSON but does not persist it to SQL or wire it into any executor.
- It assumes your emergent taxonomy (`:contract/uses`, event modes, tools) but doesn’t enforce "trigger/policy/agent/fulfillment" semantics; those are still in your head and specs, not the code.


### Admin routes \& permissions

In `register-contracts-routes!`, the backend exposes purely admin-ish endpoints:

- `GET /api/admin/contracts` – list IDs from `contracts:index`, fabricate stub metadata.
- `GET /api/admin/contracts/:contractId` – return stored EDN text + validation result.
- `PUT /api/admin/contracts/:contractId` – save EDN text, validate, and add ID to index.
- `POST /api/admin/contracts/validate` – ad-hoc validation of EDN text.
- `POST /api/admin/contracts/:contractId/compile` – run `compile-contract->sql` and return the projection.
- `POST /api/admin/contracts/:contractId/copy` – clone EDN from one ID to another, rewriting `:contract/id` as a string search/replace.

All these routes:

- Require `platform.org.create` permission via `ensure-permission!` — so they’re currently gated as “power admin” operations.
- Depend on Redis being available; if `redis/get-client` returns nil, you get a 503.

## The Vocabulary, Locked

These seven words form the complete signal-to-judgment pipeline. Everything else is either an alias or a composition.[^22_1]


| Word | Layer | Definition |
| :-- | :-- | :-- |
| **event** | eta | Anything that happened. Raw, unfiltered, no interpretation. The world wrote to you. |
| **signal** | obs | One or more correlated events from which eta (intent, meaning, cause) may be inferred. The world *might be saying something.* |
| **trigger** | contract | A named pattern over signals that, when matched, makes a contract eligible to fire. The world *is saying something we care about.* |
| **hook** | action | Code/effect that executes *because* a trigger fired. The actor *responds.* |
| **receipt** | attestation | Signed record that a specific actor did something specific during a run. "I, actor X, attest I did Y." |
| **finding** | inference | A claim derived by applying a contract-rule to evidence (signals + facts). "Given these receipts and signals, I conclude C." |
| **correlation** | judgment | A scored, evidenced link between two findings, receipts, or signals. "Finding A and Finding B co-occur with weight 0.8." |

So the full flow reads: **event → signal → trigger fires → hook runs → receipt emitted → finding produced → correlations accumulate → new events.**[^22_2][^22_1]

## Actor, Defined

An **actor** is an entity that has: (1) a stable identity, (2) a role that grants it capability, and (3) the ability to emit attestations (receipts).[^22_1]

## Sink vs. Hose

You named this correctly.[^22_1]

- **Sink** — anywhere data flows *into* the system. The system is the consumer. Examples: MongoDB, DuckDB, openplanner (the intended canonical one), LMDB, XTDB, structured file, raw log.
- **Hose** — anywhere data flows *out of* the system as a side-effect of an actor action. The system is the producer. Examples: Discord (post message), Bluesky (post note), GitHub (open issue), HTTP webhook.

A Discord *source driver* is a **source** (inbound). A Discord *post hook* is a **hose** (outbound). Same API, opposite direction.[^22_1]

The current `:sink-kind` enum in schema.edn only has `[:enum :openplanner :ragussy]`.  Ragussy is dead. The canonical sink is openplanner (via Mongo or DuckDB). Add `:hose-kind` as a separate enum for outbound targets.

## Event Loop: The Missing Piece

You are right that this exists somewhere in promethean or its submodules.  The shape you need is minimal — a **topic registry** and a **subscription** record:[^22_2][^22_1]

```clojure
;; add to schema.edn

:topic [:map {:closed false}
  [:topic/id    :id]              ;; e.g. "discord.message.create"
  [:topic/kind  :source-kind]     ;; which driver emits this
  [:topic/schema {:optional true} :keyword]]  ;; validates payload

:subscription [:map {:closed false}
  [:sub/id          :uuid]
  [:sub/topic       :id]          ;; which topic
  [:sub/contract-id :id]          ;; which contract is listening
  [:sub/filter      {:optional true} :expr-node]  ;; optional pred
  [:sub/actor-id    :id]          ;; who owns this subscription
  [:sub/status      [:enum :active :paused :drained]]]
```

The runtime contract: every source driver emits to a topic channel. Subscriptions route topic events to eligible contracts. A trigger is a named, stored subscription with a compiled filter predicate.  That is the pubsub layer, defined entirely in schema terms.[^22_2][^22_1]

## Capability vs. Policy — Resolved

**Capability** = a named bundle of tools + their default configurations that make a class of work *possible*. It implies access. You either have it or you don't.[^23_2][^23_1]

**Policy** = fine-grained environmental constraints on how you use a capability you already have. It narrows, never grants.[^23_1][^23_2]

If the actor lacks the capability, no policy is needed to prevent it — absence of capability is the lock. Policy is the deadbolt *inside* a door you're already allowed through.[^23_2]

```clojure
;; capability definitions — live in their own registry
{:capability/id    :cap/send-messages
 :capability/doc   "Compose and deliver messages to a channel."
 :capability/tools [{:name "discord" :ops ["send-message" "edit-message" "delete-own"]}
                    {:name "bluesky" :ops ["post" "reply"]}]
 :capability/data  {:default-lake "messages-outbox"}}

{:capability/id    :cap/read-messages
 :capability/doc   "Read message history and attachments."
 :capability/tools [{:name "discord" :ops ["read-messages" "read-threads" "get-attachments"]}]}

{:capability/id    :cap/search-openplanner
 :capability/doc   "Query openplanner lakes via semantic search."
 :capability/tools [{:name "openplanner" :ops ["search" "get-by-id"]}]}

{:capability/id    :cap/write-openplanner
 :capability/doc   "Upsert findings into openplanner lakes."
 :capability/tools [{:name "openplanner" :ops ["upsert" "embed" "tag"]}]}

{:capability/id    :cap/emit-receipts
 :capability/doc   "Append records to the receipt river."
 :capability/tools [{:name "receipt-river" :ops ["append"]}]}
```

A policy then looks like:[^23_2]

```clojure
;; policy — narrows, never grants
{:contract/id    "policy.discord.no-emoji"
 :contract/kind  :policy
 :contract/doc   "Prohibit emoji characters in outbound messages."
 :policy/checks  [{:expr '(not (re-find #"\p{So}" message-text))
                   :rationale "Emoji not permitted in this context."}]}

{:contract/id    "policy.discord.max-500-chars"
 :contract/kind  :policy
 :contract/doc   "Messages must not exceed 500 chars."
 :policy/checks  [{:expr '(<= (count message-text) 500)
                   :rationale "Message too long."}]}
```

Policies can reference fulfillments and intents as default check composition via `:contract/uses`.  They cannot have `:trigger` or `:role` — those belong to actors and contracts respectively.[^23_1][^23_2]

No `:agent` wrapper key. No redundant `:trigger-kind` at the top level (it's already encoded in `:contract/uses`). `:data` flattened. `:hooks` flattened. `:sink` → `:sinks`. Lakes not collections (but `:collection` is the alias we expose toward external semantic stores).[^23_2][^23_1]

## Intent — Corrected

Fires after trigger, before execution. Must return truthy or contract is skipped. Default: always true.[^23_1]

```clojure
{:contract/id    "intent.debounce"
 :contract/kind  :intent
 :contract/doc   "Skip if channel is too active for meaningful engagement."

 :intent/mode    :loose   ;; :loose | :strict | :custom

 :intent/check
 {:expr
  '(let [messages  (get-in ctx [:target :channel :messages])
         recent    (take-last 20 messages)
         chill?    (> (condition/average-ms-between recent) 2000)]
     (matches-intent chill?
       (when-not chill?
         "Channel too active for meaningful engagement right now.")))}}
```

`matches-intent` returns `{:proceed? bool :rationale string}`.  `:intent/mode` controls strictness: `:loose` means "warn but proceed if check errors," `:strict` means "abort on check error."[^23_2][^23_1]

## Fulfillment — Corrected With Two Modes

## The Execution Order, Complete

```
trigger fires (from :contract/uses "trigger.*")
  → intent check  (:intent/check expr → {:proceed? bool :rationale str})
    → [abort if :proceed? false]
  → actor resolved (actor-id → capabilities → roles → defaults)
  → contract roles merged (additional-roles / roles-override)
  → agent runs (model, system, task, tools from capabilities+policies)
    → hooks :before/hooks
    → LLM or deterministic execution
    → hooks :after/hooks (e.g. emit-receipt)
  → fulfillment check (:fulfillment/mode :strict|:loose → expr, or :judge → inline actor)
    → verdict: :held | :failed | :partial
    → new EventRecord emitted with verdict + receipt refs
  → mycology (if :failed or :partial, structured lesson appended)
```

That's the whole loop. Nothing in there requires disambiguation anymore.[^23_1][^23_2]

### 1. `promptdb/db.cljc` — the Datalog store

```clojure
(ns promptdb.db
  (:require [datascript.core :as d]
            [promptdb.core :as core]))

(def schema
  {:promptdb/fact        {:db/cardinality :db.cardinality/many}
   :promptdb/obs         {:db/cardinality :db.cardinality/many}
   :promptdb/inference   {:db/cardinality :db.cardinality/many}

   :fact/time            {:db/index true}
   :obs/about            {:db/index true}
   :inference/rule       {:db/index true}
   :inference/actor      {:db/index true}
   :attestation/run-id   {:db/unique :db.unique/identity}
   :attestation/causedby {:db/index true}
   :judgment/of          {:db/index true}})

(defn assert-record! [{:keys [kind value]}]

```

That's the whole write path. Every other system — ingestor, Knoxx agent runs, fulfillment — calls `assert-record!`.

```clojure
(defn walk-promptdb-dir
  "Walk a directory, find *.edn files, read + ingest each.
   Returns a seq of {:kind k :value v} records.
```

## The whole openplanner = model picture

```
packages/
  promptdb-core/            ← THE MODEL (cljc, platform-agnostic)
    src/promptdb/
      core.cljc             ← Malli schemas: Fact Obs Inference Attestation Judgment
      actor.cljc            ← ActorBinding ContractRef  ← ADD THIS
      db.cljc               ← DataScript conn + assert-record!  ← ADD THIS
      ingestor.cljc         ← filesystem walk → db  ← FINISH THIS
      flow.cljc             ← the obs→inference cycle shape

  signals/                  ← EventBus: emits Obs records, feeds db
  agents/                   ← Contract runtime: reads db, emits Inference+Attestation
  graph/                    ← View: queries db, renders garden/graph
  clients/                  ← View: external adapters (Discord, HTTP, etc.)
```

Knoxx (in `riatzukiza/devel`) is then **a controller process** that:

1. Subscribes to signals/EventBus (`obs` events).
2. Queries `promptdb/db` for matching actor-bindings and contracts.
3. Runs the agent contract → emits `inference` + `attestation` back into `promptdb/db`.
4. A fulfillment contract (also in Knoxx) later writes a `judgment`.

Openplanner doesn't run agents. It **stores what they knew, did, and whether it held**. That's the source-of-truth role — clean, bounded, fits in your head.
